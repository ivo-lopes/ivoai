# IVOAI v0.9.3

This stable release closes the managed OpenCode acceptance gaps while preserving
IVOAI as the session, scheduling, quota, policy, and knowledge control plane.

## OpenCode permissions

- `opencode.permission_mode` supports `interactive` and `full`. Interactive remains
  the public default; Full is a persistent IVOAI opt-in, effective on the next
  managed OpenCode session.
- The validated Full fixture completes configured operations with zero approval
  prompts. Interactive approvals remain functional.
- The policy applies to `ivoai auto` and managed `ivoai opencode`, not personal
  OpenCode or project configuration. Full does not bypass Unix permissions,
  executor sandboxing, Skill Gate, MCP isolation, or other IVOAI security policy.

```sh
ivoai config set opencode.permission_mode full
ivoai auto
ivoai config set opencode.permission_mode interactive
```

## Native OpenCode in AUTO

- Native OpenCode is an additional eligible executor, including when it is the
  only available executor. Existing Codex/Claude priority remains unchanged.
- Official provider/model discovery supplies eligible models and supported
  variants. Explicit `--planner opencode` or model selection fails closed when
  unavailable; it does not silently substitute Codex or Claude.
- Native auth discovery handles the pinned client's colored `auth list` metadata,
  including when that client emits colors despite `NO_COLOR`. No credential file
  is read by IVOAI.
- Primary and read-only worker execution reuse the controlled HTTP/SSE lifecycle.
  The native backend is separate from the managed frontend and cannot recursively
  dispatch through the IVOAI provider bridge.
- Cancellation, bounded results, Skill Gate, WorkingContext/ResultRefs, and
  session-local Memory/Context policy remain under IVOAI control.
- Failover is bounded and observable. Native errors after possible tool effects
  are not automatically replayed on another executor.
- Native quota telemetry is explicitly unknown when upstream does not expose it;
  eligibility is not a claim of unlimited quota or guaranteed provider balance.

```sh
ivoai auto --planner opencode
```

## Authentication and session isolation

OpenCode retains its own official authentication. IVOAI observes supported
non-sensitive metadata without copying tokens, cookies, or credential stores.
Codex/Claude logins are not converted into native OpenCode credentials. Missing
native authentication makes that executor ineligible, not the entire client.

Native resume requires proven authentication continuity. Account changes, logout,
stale authentication, or unprovable identity invalidate native resume mappings
conservatively rather than reusing a conversation across accounts.

## Managed frontend and TUI quality

- Managed frontend failures have explicit degraded diagnostics; supported direct
  fallback is identified as direct, never presented as a functioning OpenCode UI.
  Explicit native OpenCode fails closed if its managed frontend is unavailable.
- The IVOAI panel preserves permission mode, executor/model/reasoning, auth/quota,
  Memory/Context, server counts, and session knowledge scope. Down, stale, excluded,
  and unavailable states remain distinct instead of inventing healthy status.
- Deterministic goldens cover 12 semantic states, with 60/100/160-column layouts and
  model/variant/error projections. Updates require an explicit flag; CI only
  compares the reviewed baselines.
- Pinned OpenCode PTY tests cover attach, live resize, keyboard navigation, model
  and variant selection, prompt submission, and cleanup.

## Codex and Claude Code

Codex's capability-driven resolver and requested/effective model and reasoning
checks are preserved, without a new hardcoded version or model snapshot.
Claude Code remains a supported optional capability, including its contracts,
authentication, models, effort, and MCP integration. Personal live acceptance may
be `SKIPPED_NOT_CONFIGURED`; no Claude login is required to use another executor.

## Memory, Context, and compatibility

The Memory/Context bridge and Voicehub reproducer remain regression gates.
Multi-server federation, explicit source filters, provenance, credential isolation,
and safe write routing are preserved, with 0/1/2/3-source coverage.

Native runtime metadata remains rollback-safe for v0.9.2 readers. Native quota is
stored in an ignorable extension; native session history is preserved in a private
namespace that older versions skip and reapply can read again. Older writers may
discard reconstructible native quota telemetry, not native conversation history.

## Install, update, and rollback

Install the published binary using the release's installer from outside a source
checkout; `IVOAI_VERSION` selects this immutable release explicitly:

```sh
curl -fsSL https://raw.githubusercontent.com/ivo-lopes/ivoai/v0.9.3/install.sh | IVOAI_VERSION=v0.9.3 sh
```

For an existing managed installation:

```sh
ivoai update --dry-run
ivoai update
ivoai version
ivoai status
ivoai doctor
```

The official updater preserves compatible configuration, server profiles,
permission choice, Memory/Context references, ownership, and user-owned files.
`ivoai update --rollback` restores the prior verified binary and compatible
IVOAI-owned mutable state. Run `ivoai update` again to reapply the latest stable.
Do not replace external authentication stores or re-enroll merely to upgrade.

The binary includes the production documentation portal, including the current
[executor guide](https://github.com/ivo-lopes/ivoai/blob/v0.9.3/docs/executors.md)
and [known limitations](https://github.com/ivo-lopes/ivoai/blob/v0.9.3/docs/known-limitations.md).

## Known limitations

- Native provider authentication and provider availability remain OpenCode-owned;
  unknown quota is not unlimited, and unsupported reasoning is not invented.
- Controlled workers do not inherit arbitrary personal/project plugins or mutable
  MCPs. Full frontend approval policy does not loosen worker policy.
- The upstream OpenCode backend remains loopback-only; the embedded documentation
  server retains its separate `0.0.0.0:7780` deployment contract.
- Headroom and Ruflo remain compatibility paths. OpenViking cutover,
  NativeOrchestrator vNext, complete Monitor/Conversation Continuity, and later
  visual/i18n roadmap work are not claimed as completed by this release.
- SHA-256 checksums validate artifact integrity through the release channel; they
  are not an independent signature or attestation.
