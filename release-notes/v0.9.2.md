# IVOAI v0.9.2

IVOAI v0.9.2 stabilizes the OpenCode-first experience across Codex version selection, explicit model and reasoning choices, and Memory/Context execution. Claude Code remains a supported optional executor, using its official client authentication.

## Highlights

- One explicit Codex resolver serves direct IVOAI launches, AUTO scheduling and worker execution, with visible version and ownership diagnostics.
- OpenCode's native model picker uses freshly discovered executor capabilities. Explicit model and reasoning selections remain authoritative.
- Codex model/reasoning options preserve the MCP configuration required for Memory and Context.
- The bridge requires a completed turn and a final response, and reports structured executor/MCP failures.
- Documentation bundles build consistently across checkouts without weakening the embedded-site gate.

## Codex version management

The `LATEST_STABLE_COMPATIBLE` policy selects the newest locally available healthy, authenticated, stable Codex client that satisfies IVOAI's compatibility requirements. It considers both user/system installations and the IVOAI-managed installation, preferring an equally suitable user-owned client. This addresses launches that previously selected an older managed Codex while a newer official client was available in the operator's shell.

Resolution happens before launch. The selected executable is pinned for the session, including an integrity fingerprint. Startup does not install a new Codex version or upgrade an active session. The validated operator runtime converged on Codex 0.153.4 for the shell, `ivoai codex`, and AUTO; that observation is not a permanent latest-version pin. The current compatibility floor is 0.148.0.

`ivoai status` and `ivoai doctor` expose resolution details, compatibility, authentication state, update state and drift. An unavailable upstream check is reported as `UNKNOWN_OFFLINE`. A compatible, validated local client remains usable offline, subject to the official client's own service requirements.

For the managed installation:

```sh
ivoai update --codex
ivoai update --codex --rollback
```

The updater discovers an upstream stable release, verifies checksums, stages and smoke-tests the CLI/tool-host pair, and promotes it transactionally. It retains the prior pair for rollback and refuses changes during an active managed session.

## Model and reasoning selection

Use OpenCode's native `/models` picker and `Ctrl+T` reasoning variants inside `ivoai auto`. Runtime capability discovery supplies model identifiers, display names, supported effort levels and defaults when the official client exposes them. Persisted catalogs are diagnostic snapshots, not proof that an unavailable model is still eligible.

Automatic mode delegates selection to IVOAI policy and runtime eligibility. Explicit mode constrains executor, model and supported reasoning/effort. An unavailable explicit selection produces a structured error such as `EXPLICIT_MODEL_UNAVAILABLE`, without silently switching to another executor or model.

Requested and effective executor/model/reasoning are recorded separately. Unknown values remain unknown. Official persisted thread configuration is identified as its evidence source where per-turn telemetry is unavailable. No current model name is hardcoded to populate the picker.

## Memory/Context reliability

Codex configuration arguments are normalized before the subcommand. This fixes an argument-precedence problem in which adding reasoning configuration after `exec` could discard root-level MCP overrides, preventing Memory and Context from reaching the executor.

The Voicehub reproducer completes through OpenCode → IVOAI → Codex with Memory retrieval, a valid Context search, and a final response. An empty Context search remains a valid result.

Partial output is not accepted as a successful answer. Diagnostics distinguish nonzero exit, incomplete stream, authentication failure, cancellation, timeout, MCP tool/decode failure and bridge protocol failure when the cause is available. Bounded traces include lifecycle and tool metadata without raw provider credentials or private tool payloads.

## OpenCode AUTO

`ivoai auto` remains OpenCode-first. The managed frontend connects to the IVOAI bridge and scheduler, and keeps native model/variant controls. AUTO and explicit Codex paths, HTTP provider integration, and native attach have been exercised with the managed OpenCode artifact.

Existing multi-server selection, health and knowledge-scope visibility remain available. Authentication and model selection stay separate: the official executors own provider authentication, and users already authenticated in those clients do not need a second provider login inside OpenCode.

## Claude Code optional support

Claude Code continues to support executor dispatch, runtime model discovery, effort mapping, scheduler eligibility, explicit selection, MCP configuration and official-client authentication.

An installation without an authenticated Claude client can continue using Codex and AUTO. Claude appears eligible only when its runtime requirements are satisfied. Explicit selection of an unavailable Claude capability is rejected clearly.

Credential-free Claude unit and contract tests remain part of the normal quality gates. Live Claude integration is opt-in and reports `SKIPPED_NOT_CONFIGURED` when no authenticated official client is provisioned; configured execution and discovery failures remain failures.

## Documentation build reliability

The Docusaurus configuration now reserves the Mermaid theme key before concurrent theme initialization. This stabilizes serialized configuration order and bundle hashes. The embedded portal was regenerated through the official build process, with no documentation redesign in this correction.

Production builds, embedded-site consistency, generated CLI reference consistency and accessibility checks remain enforced. The corrective PR passed all 152 accessibility tests.

## Security

- Codex and Claude retain ownership of their authentication. Provider tokens, cookies and refresh credentials are not copied into OpenCode.
- Managed component provenance/checksum controls, staging and rollback are preserved.
- User-owned Codex provenance is reported as a native-client probe; it is not represented as an independently verified signature.
- Session executables are pinned, and bridge diagnostics retain bounded, sanitized metadata.
- Vulnerability scanning found no reachable vulnerabilities in the validated source. Existing dependency advisories that are not reachable are reported separately by the scanner.

## Upgrade

After v0.9.2 is published:

```sh
ivoai update --dry-run
ivoai update
ivoai version
ivoai status
ivoai doctor
```

For a fresh installation:

```sh
curl -fsSL https://raw.githubusercontent.com/ivo-lopes/ivoai/v0.9.2/install.sh | sh
ivoai setup
```

The release provides Linux amd64 and arm64 archives, the `ivoai-memory-context.zip` Web skill, and `checksums.txt`. Verify published checksums before using downloaded archives. Configuration, server profiles and credential references, knowledge data, provider-owned state and ownership records are preserved by the supported update flow.

## Rollback

```sh
ivoai update --rollback
```

Rollback restores the prior verified IVOAI binary and compatible managed state. After rollback, run `ivoai update` to apply the current release again. IVOAI rollback and managed Codex rollback are separate operations; `ivoai update --codex --rollback` addresses the managed Codex pair.

## Known limitations

- Model availability, quota and effort support depend on the authenticated official client. Values not exposed by that client are reported as unknown or unavailable.
- Offline resolver fallback does not make remote model inference available without the connectivity required by the provider.
- A previously configured Claude connection whose authentication has expired may cause aggregate diagnostics to show `DEGRADED`; available Codex/AUTO operation remains usable.
- Live Claude acceptance requires an independently provisioned authenticated account. An operator's lack of a Claude subscription is not a public-release gate.
- The official executor owns tool execution and permissions; the bridge exposes sanitized lifecycle events rather than reconstructing the executor's entire native UI.
- Candidate checksums belong to the locally built candidates. Published artifacts must be downloaded and verified separately after publication.
