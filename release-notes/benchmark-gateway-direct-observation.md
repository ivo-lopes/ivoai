# Benchmark: direct Gateway event observations

The test-only primary-prefetch harness now snapshots retained completed session events before launching a client, including rows with no evidence. `GatewayCodeResolves` counts only `capability.resolve` events whose capability is `evidence.code`. `GatewayCodeCacheHits`, `GatewayCodeCacheMisses` and `GatewayCodeCacheUnknown` distinguish true, false and absent `CacheHit`. The legacy `PrefetchCalls`, `StructuralCalls` and `CacheHits` still describe `code.inspect`/CodeIntel events. A cold Gateway retrieval can emit both event kinds; they are separate observations, never summed as an invocation count or inferred savings. Re-reading a snapshot replaces its counters instead of accumulating them.

The additive JSON block declares `GatewayObservationBasis=COMPLETED_SESSION_EVENTS_NOT_ECONOMY` and `GatewayCacheCondition=FRESH_APP_SESSION_NO_PREWARM`. Each benchmark row already creates its own App/session/cache state; this condition describes that construction and does not certify official-client/provider cache equivalence. Zero means no matching retained completed event, not proof that every runtime operation was observed. The projection validates the block as a whole, preserves unknown cache observations, and leaves legacy rows without the block unreported rather than inventing zeros. Economic calculations are unchanged.

The [receipt](evidence/benchmark-gateway-direct-observation/validation.json) covers mixed-event and JSON contract tests, direct-only offline Off/On controls, full App race, Python 94, App vet, and rebuilt amd64/v1 test binaries with identical discovery4. Its explicit source-pinned control expectation is zero Gateway events even when the flag is 1; the candidate's expectation is 1. Actual counters always come from stored events. A second read in the mechanism control verifies local reuse and is not a warmup or efficiency sample for the benchmark.
